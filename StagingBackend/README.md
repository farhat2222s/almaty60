# ALMATY 60 — защищённый staging backend

Отдельная серверная реализация для мобильного Unreal-клиента. Исходный `Backend` и локальная веб-игра `Playable` сохранены отдельно. Этот сервер использует PostgreSQL и проверяет право доступа, время, направление движения, прогресс миссии и одноразовое погашение. Все начальные бренды и награды **демонстрационные**. Подготовленные файлы развёртывания сами по себе не означают, что сервис уже опубликован.

## Реализовано

- Регистрация только игрока, вход, выход, блокировка аккаунта и отзыв сессий. Пароли — scrypt с отдельной солью; bearer-сессии — 256 случайных бит, в базе только SHA-256 хеш.
- Роли `player`, `staff`, `brand`, `admin`. Сотрудник и бренд привязаны к одному бренду. Администратор и служебные роли создаются только операторским CLI; публичной регистрации администратора нет.
- PostgreSQL-профиль XP/Coins, история, попытки с сохраняемыми дедлайнами и восстановлением после переподключения.
- Серверная симуляция направления движения с ограничением скорости, максимальным шагом времени, ограниченной областью и номером входного кадра. Готовая последовательность checkpoint от клиента не принимается.
- Транзакции и блокировки строк, одна активная попытка игрока, одна награда на попытку, резервирование лимита наград при старте, освобождение резерва при поражении.
- Идемпотентные start/finish/redeem. Повтор запроса с тем же ключом возвращает тот же результат; тот же ключ с другим содержимым отклоняется.
- Код награды из 256 случайных бит. В базе хеш для поиска и AES-256-GCM ciphertext для восстановления кода владельцем. Сохранённые ответы идемпотентности также зашифрованы.
- Погашение сотрудником правильного бренда; повторное погашение другим ключом и истёкшие награды отклоняются. Журнал значимых действий, лимиты запросов в PostgreSQL, базовая аналитика кампаний.
- Docker, PostgreSQL с отдельной ролью приложения и закрытым портом БД, Caddy с автоматическим HTTPS, health/readiness и миграции.

Это защищённый игровой срез для staging, а не сертификация античита. Серверная геометрия пока представляет ограниченную плоскость: полный физический мир UE, стены, транспорт, прыжки, GPS/физическое посещение и защита от ботов требуют отдельной серверной симуляции. Старт брендовой попытки переносит её серверную позицию в начало маршрута; право физического посещения этим не подтверждается. Email подтверждение, MFA, восстановление пароля, публичная модерация, push, платежи и реальные партнёрские призы не подключены.

## Установка

Требуется Node.js 24, pnpm и PostgreSQL 17/18. Используйте отдельную пустую БД; SQL исходного `Backend` в неё загружать не нужно. Публичный staging запускается только из этой папки, а не через старый демонстрационный `Backend/dev-server.mjs`. Из этой папки:

```sh
pnpm install --frozen-lockfile
cp .env.example .env
```

Заполните `.env` на своём сервере. Пароли и `TOKEN_ENCRYPTION_KEY` должны быть случайными; ключ шифрования — ровно 64 шестнадцатеричных символа (32 байта). Сохраните ключ в менеджере секретов и резервной копии отдельно от БД: его потеря делает старые коды и идемпотентные ответы нечитаемыми. Значения из `.env.example` не являются действующими секретами.

В `DATABASE_URL` для миграции нужна учётная запись владельца схемы. После миграции API запускается с ролью приложения. TLS базы проверяет сертификат; для частной сети Docker предусмотрено явное `DATABASE_INTERNAL=true`.

```sh
pnpm migrate
pnpm start
```

По умолчанию API слушает только `127.0.0.1:3080`. Native-клиент передаёт bearer-токен в памяти; не записывайте токены в публичные config-файлы или репозиторий. `/health` проверяет процесс, `/ready` — подключение к базе и версию схемы.

## Локальная интеграция без установленного PostgreSQL

```sh
pnpm local:integration
```

Запускает настоящий PostgreSQL-движок PGlite/WASM с сохранением в `data/local-integration`, тем же auth/API и автоматической миграцией на `http://127.0.0.1:3080`. Локальный ключ создаётся с правами 0600 и не выводится. Режим принудительно закрыт в `NODE_ENV=production`, сериализует все транзакции и предназначен для проверки интеграции native-клиента. Это **не опубликованный staging** и не замена сетевому PostgreSQL при нагрузке. В режиме локальной интеграции служебных аккаунтов по умолчанию нет.

## Docker и HTTPS

На выбранном Linux-сервере нужны Docker Compose, DNS-домен, входящие порты 80/443 и постоянный диск. В `.env` задайте `STAGING_DOMAIN`, случайные `POSTGRES_PASSWORD`, `APP_DB_PASSWORD`, `TOKEN_ENCRYPTION_KEY`. Для удобства безопасной подстановки в URL пароли Docker можно генерировать в hex. Домен должен указывать на этот сервер.

```sh
docker compose up --build -d
```

Compose создаёт закрытую БД, выполняет миграцию от владельца, выдаёт ограниченные табличные права `al60_app`, запускает API от непривилегированного пользователя и публикует только reverse proxy. Caddy получает сертификат автоматически. Проверка после запуска:

```sh
curl --fail https://YOUR-STAGING-DOMAIN/ready
```

Администратор создаётся отдельной операторской командой с env-переменными `BOOTSTRAP_EMAIL`, `BOOTSTRAP_PASSWORD`, `BOOTSTRAP_NAME`, `BOOTSTRAP_ROLE=admin`. Не вставляйте пароль непосредственно в историю shell. Передайте переменные из менеджера секретов или временного закрытого env-файла. `node src/bootstrap.mjs` создаёт первого admin и откажется заменять существующего. Для `staff`/`brand` также нужен `BOOTSTRAP_BRAND_ID` (например, `demo-brand`). В Compose запускайте CLI в контейнере API с явно переданными операторскими переменными. После использования удалите provisioning-переменные из рабочего окружения.

```sh
docker compose run --rm -e BOOTSTRAP_ROLE -e BOOTSTRAP_EMAIL -e BOOTSTRAP_PASSWORD -e BOOTSTRAP_NAME -e BOOTSTRAP_BRAND_ID api node src/bootstrap.mjs
```

Резервируйте PostgreSQL volume и ключ шифрования; проверьте восстановление перед подключением партнёров. Для production нужно закрепить проверенные образы digest-значениями, настроить мониторинг/алерты, ротацию секретов, антибот-защиту, отдельные ключи и политику хранения данных. Предоставленный Compose здесь не проходил фактическое развёртывание, если это отдельно не указано в отчёте проверки.

## API

JSON, максимум 16 КБ. Все маршруты, кроме auth/health/ready, требуют `Authorization: Bearer <token>`. Native-запросы без `Origin` разрешены; браузерные — только из точного списка `ALLOWED_ORIGINS`. `TRUST_PROXY=true` допустим исключительно за недоступным извне API-портом, как в Compose.

| Метод и маршрут | Данные / доступ |
|---|---|
| `POST /api/auth/register` | `{email,password,name}`. Пароль минимум 12 символов, максимум 256 байт; роль назначается `player`. |
| `POST /api/auth/login` | `{email,password}` → `{token,expiresAt,user,profile}`. |
| `POST /api/auth/logout` | `{}`; текущая сессия отзывается. |
| `GET /api/me` | `{user,profile,activeAttempt,rewards}` только своего аккаунта. |
| `GET /api/history` | Последние 100 собственных попыток. |
| `GET /api/missions` | Активные миссии; `GET /api/missions/:id` — одна. |
| `POST /api/missions/:id/start` | `{}`, player, обязательный `Idempotency-Key`. |
| `GET /api/attempts/:id` | Собственная попытка; восстановление состояния и `lastInputSeq`. |
| `POST /api/attempts/:id/input` | `{x,z,sprint,seq}`; направления −1…1, sprint boolean, seq строго предыдущий + 1. Повтор старого seq не двигает игрока. |
| `POST /api/attempts/:id/finish` | `{}`, обязательный `Idempotency-Key`. Неполная попытка завершается поражением. |
| `POST /api/rewards/inspect` | `{code}`, только staff своего бренда/admin. |
| `POST /api/rewards/redeem` | `{code}`, staff своего бренда/admin; обязательный `Idempotency-Key`. |
| `POST /api/campaigns` | brand своего бренда/admin; пример ниже. |
| `PATCH /api/campaigns/:id` | `{active:false}` или `true`, brand своего бренда/admin. |
| `GET /api/analytics` | Реальные события кампаний своего бренда/admin. |
| `PATCH /api/admin/users/:id` | `{blocked:true}`/`false`, только admin; блокировка отзывает сессии. |

`Idempotency-Key` — 16–128 символов `[A-Za-z0-9_-]`, например UUID. Один ключ относится к одной логической операции. Не создавайте новый ключ после сетевой неопределённости: повторите старый. Повтор start возвращает исходный ответ, поэтому для текущего прогресса затем нужен GET попытки. Сроки хранятся в PostgreSQL и не зависят от часов клиента; доверие остаётся к часам БД и её оператору.

Пользователь:

```json
{"id":"uuid","email":"player@example.com","name":"Игрок","role":"player","brandId":null}
```

Профиль: `{xp,coins,level}`. Уровень `1 + floor(xp / 300)`.

Ответ попытки:

```js
{
  attemptId, missionId, status: 'active' /* won | failed */,
  startedAt, deadlineAt, finishedAt, reason,
  timeLimitSeconds, totalCheckpoints, completedCheckpoints,
  targets: [{x,z}], completed: [], position: {x,z},
  movement: {walkSpeed,sprintSpeed,goalRadius,worldBounds},
  lastInputSeq, remainingSeconds, serverNow,
  rewardXp, rewardCoins, profile: {xp,coins,level}, reward, demo: true
}
```

`rewardXp`/`rewardCoins` в попытке — начисленные значения, до победы равны нулю. Планируемая награда есть в описании миссии. Последняя цель автоматически завершает попытку победой в той же транзакции, что XP/Coins и выдача кода. Последующий finish безопасно возвращает готовый результат. На нуле попытка становится `failed`, награда отсутствует. Награда: `{id,attemptId,playerId,brandId,campaignId,title,status,createdAt,expiresAt,redeemedAt,code?,demo:true}`. Код возвращается только владельцу в профиле/результате; сотрудник получает сведения о коде, который предъявлен ему игроком.

Сначала доступны `m_demo_60_checkpoint_run` и `m_arbat_60_checkpoint_run`. В Arbat-маршруте точки `[12,0], [26,5], [40,0], [54,-5], [68,0]`, ходьба 4,2 м/с, бег 7,2 м/с, радиус 1,6 м. Координата backend `x` соответствует UE X, `z` — UE Y; 1 единица backend = 100 UE units. Native-уровень задаёт свой origin отдельно. Ввод 10 Гц подходит; сервер ограничивает каждый интервал 0,25 секунды и не доверяет присланным позиции/времени/готовым checkpoint.

Создание кампании:

```json
{"brandId":"aporta","title":"Первый маршрут","type":"checkpoint","duration":60,"xp":150,"coins":60,"rewardTitle":"Демонстрационный подарок","maxRewards":100,"startsAt":null,"endsAt":null}
```

Типы `checkpoint`, `collect`, `delivery`; продолжительность 15/30/45/60/90/120; XP/Coins целые 0–500; maxRewards 1–10000. Маршрут пока берётся из Arbat-шаблона. Старт резервирует код из общего лимита кампании, победа переводит резерв в выданную награду. Таймаут/поражение освобождает резерв. Остановка кампании закрывает новые старты; уже выданный резерв действует до дедлайна попытки.

Ошибки имеют `{error,message,requestId}`. Основные коды: 401 `UNAUTHENTICATED`/`INVALID_CREDENTIALS`, 403 `FORBIDDEN`/`BRAND_FORBIDDEN`, 409 `ATTEMPT_ACTIVE`/`REWARD_LIMIT`/`REWARD_USED`/`REWARD_EXPIRED`/`IDEMPOTENCY_CONFLICT`, 429 `RATE_LIMIT`/`MISSION_COOLDOWN`. Клиентский старый маршрут `/checkpoints` намеренно отсутствует.

## Проверки

```sh
pnpm test
```

Тесты криптографии выполняются только встроенными средствами Node.js. SQL-интеграционные тесты используют PostgreSQL-движок PGlite, реальные таблицы/транзакции/ограничения и HTTP handler без открытия порта. Они проверяют регистрацию, пароли/сессии, роли, владение попытками, seq/скорость, таймаут, награду и повторы, лимиты кампании, Arbat-маршрут, collect/delivery, шифрование сохранений, блокировки аккаунта и ограничения HTTP. PGlite сериализует транзакции, поэтому не заменяет отдельный многопоточный тест PostgreSQL.

Для повторения того же набора с несколькими настоящими подключениями задайте `TEST_DATABASE_URL` **на отдельную пустую тестовую БД** (не production). Миграция создаст таблицы и демонстрационные данные; тесты создают пользователей и изменяют тестовые награды. Ничего не направляйте в пользовательскую или боевую базу.

```sh
TEST_DATABASE_URL=postgresql://... pnpm test
```

Реальные нагрузочные/конкурентные прогоны, Docker/TLS deployment, восстановление PostgreSQL, тест на iOS/Android и независимая проверка безопасности остаются отдельными этапами. Исходные подходы к транзакциям сверены с [node-postgres](https://node-postgres.com/features/transactions) и [документацией блокировок PostgreSQL](https://www.postgresql.org/docs/current/explicit-locking.html).

## Присутствие игроков (`POST /api/presence`)

Игрок с ролью `player` отправляет `{x,z,heading,driving}` (метры мира игры) и получает `{players:[{id,name,x,z,heading,driving,age}],online,radius}` — других игроков в радиусе 400 м. Записи живут 15 с в памяти процесса, `logout` удаляет запись, лимит 120 запросов в минуту на игрока. Для нескольких экземпляров нужен общий стор (Redis). CORS: браузерная игра должна быть в `ALLOWED_ORIGINS` (`local-integration.mjs` по умолчанию разрешает `http://127.0.0.1:3060`).
